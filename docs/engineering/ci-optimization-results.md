# CI optimization results and build cache evaluation

Serial database copies reduce integration execution by a median 21 minutes 24 seconds. Parallel tests reduce feedback time, but the complete job comparison increases runner consumption. The repaired cache series observes median paired complete-job savings of 23 seconds for compiler reuse and 3 seconds for package reuse. A compiler pair is 18 seconds slower despite valid reuse; these medians are not a guarantee for every runner. The earlier cache-hit sample is slower than the uncached build and does not demonstrate compiler reuse. Combined package and compiler reuse saves a median 24 seconds in three additional pairs. These measurements describe experiments; they do not establish savings for the entire production workflow.

Starting Build alongside independent checks saves 4:40 in one comparison. Four-way integration parallelism saves 12:47 of feedback time in one complete comparison but adds 20:07 runner minutes. Those exact gains need repeated complete comparisons before inclusion among repeatedly established savings. Build-change classification is verified, but its time saving is not measured.

The remaining experiments are database copies with parallel tests, affected-test selection with full scheduled coverage, reduced cache transfer, reuse of compatible build output, and reduced TypeScript or page-generation work. Turbopack remains conditional on the known compatibility issue. No time estimate is assigned to these opportunities. Cache medians, database savings and scheduling gains must not be added without a combined comparison.

## Build cache investigation

The manual cache experiment compares the complete pnpm package store and the Webpack/SWC compiler caches independently. The user explicitly authorizes private package contents in these experimental caches. Normal validation and deployment workflows retain their existing cache settings. Authentication configuration and package tokens are not cached or uploaded. Compiler packs include Server Actions key material internally, so the experiment uploads only authenticated encrypted compiler archives; the decryption key remains a runner-local secret. Encryption, compression and extraction costs count toward complete job time.

The historical compiler comparison restores 162,414,003 bytes successfully, with an exact cache-key match. Compilation takes 51 seconds in the uncached baseline, 81 seconds while populating the cache and 83 seconds after restoration. TypeScript also takes longer in the cache comparisons, roughly 25 rather than 16 seconds. These measurements do not isolate compiler reuse from runner differences.

The historical cache paths omit `.next/cache/.rscinfo`. Next includes the Server Actions encryption key in its Webpack cache version. The same-runner diagnosis now confirms that changing this key rejects the restored compiler cache. The diagnostic builds measure version equality and cached versus rebuilt modules, first with the original cache paths and then with a stable diagnostic key. The key is derived privately for the frozen measurement commit; only equality indicators reach the report.

The same-runner diagnostic at commit `20ffb143` completes four successful builds: cold 152.2 seconds, restored historical paths 153.6 seconds, stable-key cold 152.0 seconds and stable-key warm 91.4 seconds. The historical-path restore records a cache-version mismatch and zero reused modules. The stable warm build records equal cache versions, 1,999 reused client modules and 15,455 reused server modules, with zero rebuilt modules. Compilation falls from 86.0 to 26.2 seconds; TypeScript and page generation remain similar. This proves compiler reuse and a 60.6-second build saving on one VM. It excludes cache transfer, encryption and fresh-runner differences, so it is not an accepted complete-job Actions saving. [Diagnostic run](https://github.com/findmydoc-platform/website/actions/runs/37425573941).

The first pnpm measurement attempt completes its real installations, but all six baseline/population metric jobs fail afterward. The preserved first baseline records 1,397 downloaded packages, zero reused packages and a successful 14.6-second installation. The original report does not retain the exception category, so the precise cause remains unproven. A repair counts store symlink metadata without following targets and adds safe failure-stage reporting. These failed jobs stay in the experiment cost and are excluded from accepted savings; the repaired measurement uses a new namespace and frozen commit.

The historical pnpm installs report zero reused packages and 1,397 downloads. Installation takes about 11 to 14 seconds. Package-store caching is disabled in those comparisons, so these values are expected and do not demonstrate a broken restore.

The repaired pnpm comparisons at `ebfb0d9f` complete all 15 measurement jobs successfully. Complete baseline/population/warm seconds are 35/36/32, 35/39/35 and 36/34/32. Paired savings are 3, 0 and 4 seconds: median 3 seconds, range 0–4 seconds. This is a small observed gain, with one pair showing no gain. Cold installs download 1,397 packages and reuse none; all exact and fallback restores reuse 1,397 packages and download none. All changed-lockfile comparisons miss the cache and download again. The complete store is about 1.134 GB uncompressed, while uploaded caches are 303.76–303.90 MB. Restore and extraction take 7–9 seconds for exact hits; compression and upload take 5–6 seconds on population. These costs explain why shorter installation does not translate into an equally large complete-job saving. [Repaired measurement](https://github.com/findmydoc-platform/website/actions/runs/37428462208).

The repaired compiler series at the same frozen commit completes all 12 fresh-runner jobs and the four-build diagnosis. Complete baseline/population/warm seconds are 207/233/184, 209/257/149 and 152/209/170. Paired savings are 23, 60 and −18 seconds: median 23 seconds, range −18–60 seconds. Initial population adds 26, 48 and 57 seconds. All warm builds reuse 17,454 modules and rebuild none; all three source changes verify the new title, reuse 17,452 modules and rebuild four. The negative pair remains in the result. Its cold runner has an AMD EPYC 9V45 CPU and its warm runner an EPYC 9V74 CPU; the build itself falls from 93.6 to 73.3 seconds, but restore and other job work outweigh that gain. Hardware and setup differences are measured confounders, not cache failures.

The combined comparison starts only after all independent reuse, fallback, lockfile and source-change gates pass with positive median paired job savings. Complete baseline/population/warm seconds are 231/252/150, 216/266/192 and 180/261/157. Paired savings are 81, 24 and 23 seconds: median 24 seconds, range 23–81 seconds. The comparison proves simultaneous reuse and complete-job savings; it does not isolate pnpm's extra benefit over compiler caching alone. Independent and combined savings must not be added.

The repaired series consumes 89:10 physical runner minutes across 37 successful measurement jobs and two reporting jobs. Together with the preserved first series, cache investigation consumes 147:51 physical runner minutes, including the six failed metric jobs. GitHub's timing API reports zero billable milliseconds for both runs while the repository is public. A future private-repository quota saving is not measured here. All data is independently revalidated locally against the completed Actions job timestamps and cache receipts; negative measurements remain included.

The measurements are frozen at `ebfb0d9f35379afce9b3f7e29c891ed6e6c16884`, using Node 24.14.0 and pnpm 10.28.2. A subsequent workflow-only retention correction also preserves the original installation and compiler JSON when a combined measurement cannot be assembled; it does not alter builds, cache identities or timing calculations. Local validation covers 68 targeted tests, `pnpm check`, workflow lint and formatting. Ordinary CI cache settings are unchanged. Test, Architecture and Security reviews are recommended before adoption and have not been run.

The reusable cache workflow is invoked only by the manually dispatched integration diagnostic workflow on the experiment branch. Three fresh-runner rounds compare uncached installation, initial cache population and exact reuse. Additional checks exercise fallback restoration and a changed React dependency specifier with the same resolved version, proving cache-key invalidation without changing installed package versions. Compiler comparisons follow successful same-runner diagnostics and verify a changed metadata title in generated server output.

Only successful processes with measured package or compiler reuse qualify as working warm caches. Reports distinguish initial population cost, complete job runner time and the relevant build phases. A combined three-pair comparison runs only when both independent comparisons show positive median net savings. Failed measurements remain diagnostic evidence. No cache benefit is accepted from a restore receipt alone.

Security, Test and Architecture reviewers are recommended before adoption. They run only after explicit user confirmation. Runtime cache policy and public freshness behavior are outside this experiment.

## Recording subsequent experiments

Each result records the broad approach, scope and source commit, comparison count, before/after duration, elapsed feedback, summed runner time, setup cost, correctness evidence and a link to retained evidence. Unmeasured potential stays separate from accepted savings. Failed and rejected measurements remain diagnostic evidence. Report rollout separately from experimental completion and do not add savings from untested combinations.
