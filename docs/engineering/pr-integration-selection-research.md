# PR integration selection research

Research snapshot: 7 October 2026. The practical first opportunity is a test-only PR routed to its changed integration files. The retained history provides no evidence of additional truly irrelevant PRs currently receiving integration tests. Deferring relevant tests to Main or nightly runs changes failure timing and requires an explicit policy decision. It is not an empty affected-test selection.

This report covers routing policy and history, not collection dependency topology. No tests, Actions dispatches, product or workflow edits, commits, deployments, or formal reviews were performed. Raw evidence remains unchanged. The earlier Euler Vitest research is reused and checked against installed Vitest 4.1.11.

## Observed implementation and its limits

Two sources must remain distinct:

- The experiment branch at `822c3f42265f721a0318398e3833b2430dfdd09f` has serial integration execution and a path gate. See [.github/workflows/deploy.yml, lines 67–79 and 391–433](https://github.com/findmydoc-platform/website/blob/822c3f42265f721a0318398e3833b2430dfdd09f/.github/workflows/deploy.yml#L67).
- The primary checkout has concurrent, uncommitted implementation work. Its `.github/workflows/deploy.yml` at lines 63–75 retains that integration gate, while `:403–537` introduces four shards and a merge named `Integration Tests`. `:10–27` and `:85–103` add nightly integration routing. The primary snapshot of *.github/filters/build.yml* at lines 1–30 applies `every` to build exclusions; `deploy-preview.yml` consumes the same build filter. These are working-copy observations, not a claim that the candidate is deployed. The primary snapshot of *docs/engineering/ci-performance-measurements.md* at lines 73–79 explicitly leaves affected integration selection to [issue #2049](https://github.com/findmydoc-platform/website/issues/2049).

The integration gate covers access, API routes, auth, collections, seeds, hooks, migrations, Payload config, the database harness, integration tests, setup, and Vitest config. It does not cover `src/features/**`, `src/plugins/**`, `src/utilities/**`, shared fixtures/helpers, or dependency manifests. An omitted path cannot establish irrelevance. For example, [transactionalEmail.delivery.test.ts:9–24](https://github.com/findmydoc-platform/website/blob/822c3f42265f721a0318398e3833b2430dfdd09f/tests/integration/transactionalEmail.delivery.test.ts#L9) imports feature code and fixtures excluded by the gate. This is a selection gap, not proven missed failure detection in a historical run.

Docs, isolated stories/UI, and ordinary tooling paths already produce no integration job unless another changed path matches. Pure UI is not a blanket exemption: server actions, endpoint behavior, permission inputs, or filesystem contract scans can connect a UI change to integration behavior. Test-only also needs subdivision. Changes to unit/tooling/Storybook tests are already excluded; integration-test changes trigger the whole suite; shared setup must remain broad.

The primary candidate runs complete integration on nightly/manual events. Main execution still depends on `deployable`, and push-level exclusions remain. Thus it does not run the complete suite on every Main push. A later full-Main policy should define which test/config-only pushes require integration independently of build relevance.

## Marginal economic bounds after database copies

The accepted copy evidence is `tmp/ci-diagnostics/db-copy-media-37386841643/full-summary.md`, with three copied-suite durations of 773.935, 781.426, and 778.499 seconds. Median residual work is about 13 physical minutes. It includes services, migrations, template preparation/seeding, copies, instrumented tests, reporting/merge, and cleanup, but excludes shared dependency installation and VM startup. See [accepted run](https://github.com/findmydoc-platform/website/actions/runs/37386841643) and [ci-optimization-results.md:9–14](https://github.com/findmydoc-platform/website/blob/822c3f42265f721a0318398e3833b2430dfdd09f/docs/engineering/ci-optimization-results.md#L9).

- A genuinely irrelevant PR could avoid approximately that entire 13-minute component if classification happens before services and template preparation. No additional such PR is established here.
- For #2019, gross avoidance is bounded by zero to about 13 minutes within this measured component, conditional on the historical workload. Three selected files still need setup, so the upper bound is deliberately loose. No positive net lower bound is established, and file-count ratios cannot predict duration.
- The observed 1/50 narrow candidate gives at most about 13 gross physical minutes across this sample under a one-run-per-PR assumption. Actual rerun frequency and selected duration are absent. This is an opportunity envelope, not measured savings or a monthly forecast.
- The primary candidate's four-shard execution has no combined database-copy measurement. Neither its older 47:22 physical runner total nor the old 34-minute serial baseline is a valid marginal savings baseline after copies.

Use `net physical work avoided = avoided optimized PR work − selector overhead − additional scheduled work − additional fallback work`. Retained Main/manual work cancels only if unchanged. If seven new weekly full serial-copy runs cost the same residual component, they add roughly 91 physical minutes before installation/startup. One maximum-avoidance #2019 run removes at most roughly 13, leaving about 78 additional minutes in that conditional scenario. Seven complete avoided executions are only an optimistic break-even point; partial selection requires more. If nightly runs are already adopted, their incremental cost for selection is zero, but their cost still belongs in accounting for the combined policy change.

GitHub rounds billable job time separately. Exact billed-minute savings require before/after job durations and repository/runner billing context, not total physical seconds divided by 60. [GitHub job execution time](https://docs.github.com/en/actions/how-tos/monitor-workflows/view-job-execution-time). Whole-workflow latency also depends on concurrent Build/Storybook work and is not bounded by this component alone.

## Unproven routing recommendation

Use a policy with separate outcomes: `irrelevant`, `selected`, `full`, and `classification-failed`. An empty selection is accepted only when every changed path is explicitly irrelevant to integration. A relevant path with no proven test mapping receives full validation. Intentionally deferred relevant tests require a separately named policy and disclosure of later failure detection.

| PR change                                                                                                   | Proposed integration policy                                                                                                  |
| ----------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Only nongenerated docs, isolated story assets, known metadata or non-runtime tooling                        | Zero integration tests with an explicit reason; retain existing security/static/tooling checks                               |
| Only concrete integration test files                                                                        | Changed files, plus contract inventory checks affected by test additions/deletions; shared test dependencies widen selection |
| Product behavior with verified ownership mapping                                                            | Union of related files and explicit HTTP/database/filesystem/security contracts                                              |
| Auth/access/hooks, migrations, plugins, shared config/harness, dependency or unknown runtime changes        | Full suite until a reviewed mapping preserves their assertions                                                               |
| Failed diff/discovery, missing revisions, truncated API files, unresolved imports, unknown removals/renames | Full fallback; fail the stable gate if full execution cannot establish success                                               |

Whole-PR discovery should bind event base/head SHAs, compute their merge-base, and inspect `git diff --name-status -z --find-renames <merge-base> <head>`. Include both rename paths and deleted paths. Do not execute removed test filenames; select their surviving consumers/contracts, or fall back. Inspect the PR head for selection and validate the intended merge result. A synthetic merge checkout must not silently substitute base-branch-only changes for the PR diff. [Git diff](https://git-scm.com/docs/git-diff). The existing path action uses the PR file API for PRs and merge-base Git discovery in other modes. [paths-filter](https://github.com/dorny/paths-filter). Paginate API evidence and cross-check completeness; GitHub caps PR file responses at 3,000 files. [GitHub PR files API](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests-files).

Keep a stable, always-emitted integration decision check. It should verify classification success, expected selected reports and passing assertions, or an explicit irrelevant decision. Classifier failure, upstream failure, cancellation, and missing reports must never turn into an unexplained green skip. The primary candidate merge currently skips when shards skip, so it does not provide that full decision contract.

Read-only `gh api repos/findmydoc-platform/website/rules/branches/main` reports seven required contexts: `lint pr title`, `Static Checks`, `Unit Tests`, `Storybook Tests`, `Build`, `Dependency Review`, and `db-quality-gate`. `Integration Tests` is not currently required by that response; legacy branch protection returns 404. Adding a required integration decision gate is a separate policy change. GitHub accepts successful/skipped/neutral required checks, while filtering out an entire required workflow can leave it pending. [Protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-status-checks-before-merging), [workflow filtering](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax).

Coverage needs two honest contracts. Full Main/nightly/manual suites retain all assertions, current full-suite file inventory, and 50% thresholds in `config/coverage/vitest.thresholds.integration.js:1–12`. Selected PR execution reports selected test identities and scoped coverage separately. It must not publish partial artifacts as complete integration/combined coverage or lower full-suite thresholds. `--changed` also narrows coverage, including explicit includes, as installed `coverage.DM_a_rWm.js:679–693,778–788` confirms. [Vitest coverage.changed](https://vitest.dev/config/coverage.html#coverage-changed). Existing integration includes are at `vitest.config.ts:58–68`; combined reporting scans available summaries at `scripts/coverage/merge-coverage.mjs`, lines 20–42. A partial result cannot preserve the full PR coverage guarantee by merely keeping the same percentages. If policy requires that complete guarantee on every relevant PR, selection must remain advisory until full validation still runs.

## Effort, blockers, and smallest validation

Complexity is medium for an explicit test-only/irrelevant policy and selection replay. Failure routing, stable checks and partial coverage need separate validation. General product selection is high complexity because semantic ownership and runtime consumers must be represented. Calendar estimates are not used. No security, auth, access, or hook assertion should be removed or weakened.

The blockers are missing semantic ownership guarantees, unknown selected-run timing after copies, no rename evidence, and approval of the coverage/risk-timing policy. Correcting existing false-negative paths may offset savings. The primary candidate is still changing, so implementation must recheck its final gates and contexts.

The smallest later validation is a bounded, nonexecuting selection comparison for #2019 and representative feature, docs, fixture, setup, rename/delete, and failed-diff inputs. First audit the discovery lifecycle, then compare selected file manifests and reasons without running suites. Only if selection is useful, reuse an existing full-copy receipt and measure one selected-copy execution; no new full performance series is justified. Test, architecture, and workflow-security reviews are appropriate before adoption, but none were run for this research.
