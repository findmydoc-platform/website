## Findings supported by code and retained evidence

A small file selection can retain the full production Payload configuration and the baseline database copy. Test selection and configuration size are separate decisions. The existing diagnostic config already inherits the integration project and appends per-file baseline-copy setup, while allowing an explicit `include` list. Selected files still initialize their usual Payload config. See [scripts/ci-shard-diagnostics.mjs:256](https://github.com/findmydoc-platform/website/blob/822c3f42265f721a0318398e3833b2430dfdd09f/scripts/ci-shard-diagnostics.mjs#L256), [tests/setup/integrationBaselineCopy.ts:5](https://github.com/findmydoc-platform/website/blob/822c3f42265f721a0318398e3833b2430dfdd09f/tests/setup/integrationBaselineCopy.ts#L5) and [tests/fixtures/ensureBaseline.ts:13](https://github.com/findmydoc-platform/website/blob/822c3f42265f721a0318398e3833b2430dfdd09f/tests/fixtures/ensureBaseline.ts#L13). Vitest supports positional file filters, and setup files execute before each test file. Payload initializes from the supplied config and dispatches Local API operations by collection slug. [Vitest CLI](https://vitest.dev/guide/cli.html), [Vitest setup files](https://vitest.dev/config/setupfiles.html), [Payload Local API](https://payloadcms.com/docs/local-api/overview).

This establishes a cheap execution mechanism, not a proven safe affected-test selector. Full config imports make generic import reachability broad; collection relationships and hook calls introduce dependencies that test imports alone cannot represent. The smallest useful implementation keeps full config, baseline preparation, per-file copies and normal hooks, and changes only the executed file list. Creating smaller config profiles is unnecessary for that approach.

### Why Country and Gallery both select

The retained domain POC journal records both groups for every Country and Gallery scenario with `fallback: false`. Reasons explicitly name each changed file against both groups. Thus this result is dependency-manifest intersection, not an unknown-path fallback. The current static inventory returns **the same 37 collections and 274 dependency files for each group**, including both `Countries.ts` and the Gallery entry hook. ## Unproven recommendations and smallest validation

Prefer a small explicit file/consumer map over config restructuring. Preserve existing files/assertions and full config. Start with test-only changes selecting their exact file plus affected shared fixtures, then narrow source leaves with clear consumers. A private Gallery hook change can initially select Gallery files plus clinic-profile behavior and shared contracts; a schema, shared ownership/access, storage or baseline change selects every known consumer or the full suite. This recommendation has not established identical failure detection.

Use the full suite as the fallback for unknown, deleted or renamed paths without a verified mapping, package/lockfile changes, full config/plugins/globals, test/database harness or shared fixtures, schema/migration wiring, unresolved imports, and broad seed/storage dependencies. Shared runtime code does not become irrelevant merely because a boundary is excluded from the import graph. Smaller plugin profiles or eliminating collection cycles would require ongoing config parity and behavior work; no measured result supports that larger investment.

Smallest next validation is a read-only selector replay over explicit synthetic changes and existing receipts. Check a Gallery hook, Country schema, email-only leaf, shared fixture, source-scan input, rename and unknown path. Assert exact selected filenames and fallback reasons without importing test modules or initializing Payload. Price omitted file phases with the existing E-0 records. Only if this demonstrates a useful minute-scale budget should a later authorized paired execution compare full-config/full-suite DB-copy against full-config/selected-file DB-copy on one runner. Keep scheduled cost and aggregate coverage handling explicit. No execution validation was performed here.

Complexity is medium for an initial explicit map and static replay, and high for comprehensive runtime consumer auditing. A focused execution comparison adds isolation and coverage validation. An exhaustive automatic soundness claim or separate Payload profiles is substantially broader. Blockers are dynamic collection calls, source/data reads, shared startup side effects, lack of a measured selected-file run and subset coverage compatibility. Full-suite aggregate thresholds cannot simply be treated as satisfied by subset coverage.
